# Generated browser provider routing

This is source implementation evidence. No browser, model, build, executable check
or test was run during the owner's implementation phase.

`VideoStudioCinematic.renderPortal`, `VideoStudioTemporal.renderTemporalMotion`
and `VideoStudioNeural.generateKeyframes` capture the supplied project/device
pair before their first asynchronous operation. A remote call requires both
IDs. An ordinary owner call may capture the current local selection once. Media
restore, nested neural anchor generation and the subsequent project refetch all
retain that same pair.

Generated bytes are committed to the local IndexedDB asset store before project
registration. Registration uses `POST /api/projects/:id/append-generated` with
only the newly generated assets, stable-ID clips and provider generation patch.
The Worker merges those additions with the current graph transactionally.
Captured old asset/timeline arrays are never used for generated registration.
Other provider project patch helpers carry the captured content revision.

Successful registration requires an acknowledgement naming the captured
project/device and containing every new asset/clip ID with identical canonical
metadata. HTTP 409 is an explicit
registration conflict; another 4xx is rejected; a transport, 5xx or malformed
acknowledgement leaves registration unconfirmed. Each failure result retains
the exact asset/clip metadata and IDs, says that local bytes are preserved and
forbids automatically rerunning generation. Registration can be retried with
those same IDs without regenerating media. The endpoint accepts identical ID
replay, rejects differing metadata collisions and does not reapply stale
generation fields on a complete identical replay.

If a later neural frame fails after earlier frames were saved, an explicit
partial-unregistered result preserves those saved frame IDs. Temporal generation
propagates a failed anchor registration and does not silently render older
anchors. Optional Drive upload happens before the append so acknowledged Drive
references are included in asset metadata. Original local media is retained.

Future browser/provider cases, authored as scenarios and not executed:

- Pause each provider at its first asynchronous operation, switch both owner
  selections, resume, and confirm every fetch, restore and append uses the
  original captured pair. A remote call missing either ID must fail before work.
- Complete a concurrent owner edit while rendering. The generated append must
  preserve that edit, append each new stable ID once, and increase the current
  content revision. A heavy captured-revision patch must reject a stale revision.
- Drop the append response after the Worker commits. Confirm the unconfirmed
  result retains local bytes and exact IDs; replaying that registration must
  reuse the existing entries without overwriting newer generation metadata.
- Collide an asset or clip ID with differing metadata. Confirm explicit conflict,
  retained generated bytes, and no success toast or success-triggered reload.
- Return HTTP 200 with wrong project/device, missing or differing generated
  metadata, or invalid
  response JSON. Confirm registration remains unconfirmed and no provider reruns.
- Fail neural frame two after frame one is durably saved. Confirm its partial
  result contains frame one's exact ID/metadata; Temporal must stop before flow
  inference rather than select older anchors.
- Finish auto-upload, then append. Confirm the registered metadata includes the
  returned Drive file ID. Reject registration and confirm the recovery metadata
  still contains that reference and the local generated bytes remain available.

Browser termination during a prepared operation still has an explicitly unknown
side-effect outcome. The parent runtime's durable receipt prevents automatic
provider replay; a generated media result is not proof of decoded playback,
model correctness or verified export quality.
